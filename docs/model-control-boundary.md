# TOE-DAC 模型判断与确定性控制边界

## 设计结论

TOE-DAC 的 Target、Observe、Estimate、Decide、Act、Check 每个阶段都包含不可省略的
模型判断。确定性控制层不是阶段替代器，而是为模型阶段提供可验证事实、机械执行能力和硬约束。

基本不变量：

> 模型决定“做什么、为什么、是否足够”；控制层负责“按规范执行、保存、登记和校验”。

任何阶段都不得因为存在确定性规则而绕过模型；任何纯机械操作也不得被包装成一个需要模型反复
规划、确认和验收的 Action。

## 架构不变量与经济性约束

TOE-DAC 不是为单次简单任务追求最低延迟的快速路径，而是面向长周期、可恢复、
可追溯和可替换模型的通用控制协议。设计和优化必须同时遵守以下不变量：

1. 任务必须显式经过 Target、Observe、Estimate、Decide、Act、Check 六个责任块。
2. 每个责任块必须有大模型参与关键语义判断，不得退化为只由硬编码规则驱动的特定场景流程。
3. 阶段边界、结构化交付物和状态转换必须保持明确，使不同模型可在相同协议下替换、比较和回放。
4. 性能优化不通过删除阶段或取消关键模型判断实现，而是通过减少重复上下文、无效输出、
   机械性工具往返、整阶段重做和无信息增量的重试实现。

对于一般任务，TOE-DAC 相对“单次直接模型调用”的平均时间和 Token 成本以约 **10×**
为参考上界和准约束。该指标不是对每一次任务的硬性承诺，但超出时必须能够由真实的风险、
工具耗时或恢复价值解释，不能来自框架的空转。

这一局部成本是为全局可靠性付出的投资：在长周期、多 Action、多 Session 的项目中，
通过减少返工、无效探索、上下文丢失和人工跟进，目标是使项目级时间与 Token 总成本约降低
**2×**。比计算成本更重要的收益，是将人从连续的项目进程中解放出来，只在里程碑和不可自动恢复的
异常处参与。

因此，性能与可靠性必须同时度量：

- 单任务记录阶段耗时、模型调用次数、Token、工具调用次数、重复工具调用和恢复收益；
- 项目级记录人工中断次数、返工率、断点续行成功率、里程碑一次通过率和经验采纳后的节约；
- “阶段已执行”不代表产生了价值；每次模型或工具往返都应当产生新判断、新事实、新产物或明确的风险收敛。

## 六阶段职责矩阵

| 阶段 | 模型的关键判断 | 确定性控制层职责 |
| --- | --- | --- |
| Target | 理解用户意图，定义正向/负向目标和验收语义，识别实质歧义 | 分配 ID、补齐协议默认值、校验 Schema、移除用户未提出的路径和数值硬约束 |
| Observe | 决定需要观察什么、选择来源和技能、区分事实/推断、判断事实是否充分 | 执行已选工具，创建 Session 证据目录，保存截图，计算哈希，登记工具原始元数据 |
| Estimate | 判断可行性、风险、成本、信息缺口以及是否需要重新观察 | 补齐纯记账字段、校验枚举和字段结构、记录阶段耗时与用量 |
| Decide | 选择解决路径，生成有依赖关系的 Action 图，确定预算和升级条件 | 分配 Action/断言 ID，校验 DAG，删除“复制证据”“再次验收”等机械或重复 Action |
| Act | 执行 Action 的语义工作，生成报告、代码或决策结果，并根据失败反馈调整 | 调用受限 Executor，原子写入 Artifact，关联证据，记录尝试与预算 |
| Action Check | 判断 Action 结果在语义上是否正确、完整并实现 Action 目标 | 计算文件存在、哈希、包含、长度、证据引用等硬事实；硬事实交给模型审查但不可被改写 |
| Target Check | 判断整体结果是否真正实现 Target，并检查负向约束 | 汇总验收硬事实、持久化结果和完成 Artifact；失败后按预算触发恢复 |

Check 在工程上分为 Action Check 与 Target Check，因此模型判断与确定性预检查也分别执行。

## Target 与证据的边界

Target 必须与用户意图对齐，只定义最终效果、负向边界和效果验收语义。
Target 不关心证据如何生成、命名、存放或归档，也不得将以下内容写入 positive 或
acceptance criteria：

- canonical evidence directory、`./evidence/` 或其他存储路径；
- 截图、JSON、日志、哈希、复制或归档方式；
- `evidence_exists` 等只能证明留痕存在、不能证明用户效果实现的验收条件。

即使用户明确提出“保留证据”，也应将它解释为运行时留痕约束，而不是业务 Target。
例如“访问网页、确认标题与主要内容、生成中文报告并保留截图证据”的 Target 只验收网页事实和
中文报告；截图由 Observe 运行时自动留存。

## 阶段证据不变量

证据留存是每个 TOE-DAC 阶段的天然责任，不需要模型将其规划为 Action。
控制层根据操作类型选择证据形式：

| 操作类型 | 必须留存的原始证据 |
| --- | --- |
| 阶段模型判断 | 当前 `submit_*` 的结构化 JSON |
| 命令行/脚本 | 命令参数、Job ID、状态、exit code、stdout 和 stderr 的 JSON |
| API | 规范化请求摘要、响应体、状态码和重试记录 JSON |
| Web | 页面截图，以及 URL、title、body/snapshot 和观察时间元数据 JSON |

证据文件必须以所属阶段名为前缀，例如 `target-*`、`observe-*`、`estimate-*`、
`decide-*`、`act-*` 和 `target_check-*`。证据实体位于 Session trace 内，`/evidence` 只是只读访问入口。

如果 Act 会改变服务、文件、配置、容器或其他可观察状态，Action 必须标记
`changes_state=true`，并形成三段证据链：

```text
act-before-*  变更前状态
act-action-*  实际变更操作及原始结果
act-after-*   变更后状态与验证
```

缺少 before、action 或 after 任一必需证据时，Act 不得通过并进入 Check。

## Observe 的正确流程

```text
模型读取 Target 和技能索引
→ 模型判断需要访问哪个来源并选择工具
→ 运行时执行工具
→ 控制层把截图保存到 trace/sessions/<session>/screenshots/
→ 控制层登记 path、sha256、size、URL、page_title、body_text 等原始元数据
→ 模型依据工具结果提交 Observation，判断 facts 与 unknowns
```

控制层不能仅因用户输入里包含 URL 就直接构造 Observation。相反，模型也不能决定截图应该复制到
哪个内部目录、如何计算哈希或是否需要再做一次“归档 Action”。

## Check 的正确流程

```text
控制层计算硬事实
→ 模型审查硬事实，并判断语义正确性与整体覆盖度
→ 合并结果（硬事实优先，模型补充语义判断）
→ 状态机决定通过、预算内自动恢复或请求人类
```

预算内的重试、内部 Plan/断言冲突、字段形状不一致都不是新的用户授权，不应打断人类。只有缺少
用户才能提供的信息、凭证或新增高影响授权时，才进入 `waiting_human`。

## 当前控制层结构化范围

- canonical Session 目录和 Artifact 目录分配；
- 截图等文件的保存、路径约束、哈希和证据注册；
- event/operation/messages/evidence 的追加式落盘；
- Schema、枚举、DAG、预算和状态转换验证；
- 用户未提出的 `./evidence/`、复制/归档 Action 和重复验收 Action 清理；
- 用户未明确给出的数值限制不提升为硬验收标准；
- 网络/模型运行错误归一化后进入有预算的自动恢复；
- 确定性断言计算，以及与模型语义审查结果合并。

## 性能与收敛设计

### 阶段不等于无限模型循环

六个阶段都必须保留模型判断，但每个阶段应当有明确的最小交付物和收敛条件。
一次工具调用、一次后台任务状态查询或一次 Schema 修复，不应当自动扩张为一次新的完整阶段探索。

参考调用预算：

| 阶段 | 正常模型往返 | 允许的附加往返 | 不应发生 |
| --- | ---: | --- | --- |
| Target | 1 | 1 次受限结构修复 | 因工具能力未观察而改写用户目标 |
| Observe | 2–3 | 受限的工具换路 | 模型轮询后台 Job，或失败后重做已成功观察 |
| Estimate | 1 | 1 次受限结构修复 | 重新执行 Observe 工具 |
| Decide | 1 | 1 次受限结构修复 | 将证据搬运、查询和重复验收规划为 Action |
| Act | 每个 Action 1–2 | 有新证据的路径重试 | 让模型执行文件落盘、Job 轮询等机械操作 |
| Check | Action/Target 各1 | 未解决的语义断言 | 要求模型重算已由控制层确认的硬事实 |

这个预算保留六阶段和双层 Check，同时使普通单 Action 任务能够接近 10 次模型往返的参考约束。

### 阶段级检查点

每一个工具调用完成后，控制层必须持久化以下检查点：

- 调用指纹：阶段、Skill、工具、规范化参数和目标对象；
- 运行状态：planned、running、succeeded、failed 或 unknown；
- 结果与证据引用；
- 已获得的信息增量和仍未解决的缺口；
- 是否可幂等重放，以及重放前提。

恢复时从最后检查点继续。同一调用指纹已经成功时，默认直接复用证据；只有证据过期、
用户修改目标或模型明确说明新的信息需求时才可重做。

### 后台任务与工具调度

模型决定调用哪个 Skill、执行什么操作及如何解释结果；控制层负责实际调度。
异步 Job 的 status 轮询、超时、输出偏移和完成通知是控制层行为，不消耗模型往返。
多个无依赖工具调用可并行执行，其结果一次性回传给当前阶段模型做语义收敛。

Skill 采用渐进加载，但已加载状态和适用范围必须在 TD/Session 内持久化。
一个阶段只加载与当前缺口直接相关的 Skill，不得为预防性探索一次加载全部 Skill。

### 结构化输出修复

结构化输出失败必须与工具失败分类。修复顺序为：

1. 本地解析与规范化：工具 arguments、纯 JSON 文本、Markdown JSON 和可安全解开的双重编码；
2. Schema 本地校验，返回精确的字段错误；
3. 如仍需模型修复，只暴露当前 `submit_*` 工具，不再开放 Skill 和执行工具；
4. 修复只修复当前结构交付物，不重做已完成的观察或 Action；
5. 相同错误指纹连续出现时，不得继续使用相同路径空转。

证据必须保留模型响应的 `content`、`tool_calls`、`finish_reason`、解析路径和精确失败类型。
`structured model output must be an object` 这类统一错误不足以支持回溯，必须区分缺少阶段工具、空响应、
非对象参数、无效 JSON 和 Schema 不匹配。

### 上下文投影

不同阶段只接收完成判断必需的投影：

- Target：用户原始需求、有效澄清和与目标直接相关的约束；
- Observe：Target、已有证据摘要、未解决缺口和可用 Skill 索引；
- Estimate：Target 与 Observation，不重复携带原始工具长输出；
- Decide：Target、Observation、Estimate 及可用 Executor 契约；
- Act：当前 Action、相关证据和上次失败差异；
- Check：被检对象、确定性检查结果和仍未解决的语义断言。

原始对话、全量 Skill 文档、全量工具输出和已在上游固化的结构不应在每个阶段重复注入。

## 当前实现问题的判定标准

以 `sess-cbca95fc-20260810_205117` 的只读服务器勘查为例，直接 SSH 收集系统、CPU、内存、
磁盘和容器信息的墙钟时间约为 1.21 秒，而当前 TD 在 Target 与 Observe 中发生了以下非必要成本：

- Target 在未进入 Observe 验证 SSH 能力前，将“root 登录勘查”改写为“公开外部侦察”；
- 新 Target 额外引入浏览器截图和搜索要求，造成与原需求无关且对关闭的 HTTP/HTTPS 服务不可完成的验收条件；
- Observe 每次最多执行 8 轮模型/工具循环，失败后整阶段重做 4 次，共消耗 32 轮；
- 四次 Observe 中累计执行 28 次 `run_skill_script`、7 次搜索和 8 次浏览器观察，已成功的 SSH 事实未成为恢复检查点；
- `status` 调用预算按脚本和操作名共享，未按 `job_id` 隔离，不同 Job 的正常查询被误判为超预算；
- 相同 `progressive skill/tool loop exceeded 8 rounds` 被记录为多条新经验，但没有在下一次重试前禁止已证明无效的同路径。

这些问题不说明六阶段过多，而说明当前实现还没有满足“阶段内收敛、阶段间复用、恢复不重做”。

## 优化优先级

1. **P0：保真 Target**。为 Target 的 positive、negative 和 criterion 增加需求来源；禁止因当前能力判断擅自降级用户目标。
2. **P0：Observe 检查点**。持久化工具调用指纹、Job 和已获事实；恢复仅处理未完成缺口。
3. **P0：Job 机械调度**。由控制层异步监听并合并结果，不让模型调用 `status`；预算按 `job_id` 隔离。
4. **P0：修复通道隔离**。Schema 修复只开放 `submit_*`，保留原始响应，取消“内层修复失败后外层整阶段立即重做”。
5. **P1：上下文投影**。取消每阶段固定携带最近 30 条对话和所有已加载 Skill 全文，改为阶段特定摘要。
6. **P1：经验去重与前置利用**。相同指纹更新同一经验；重试前先由模型采纳或拒绝，已失败的相同策略默认不再提供为首选。
7. **P1：成本预算。** 新增阶段与 TD 级模型调用、Token、墙钟时间、工具调用和重复指纹预算，超出 10× 参考线时产生可解释记录。
8. **P1：回归门槛。** 单 Action 实测必须断言六阶段的模型决策证据都存在，同时断言无重复成功工具调用、恢复从检查点续行且成本接近参考约束。
