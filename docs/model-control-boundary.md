# TOE-DAC 模型判断与确定性控制边界

## 设计结论

TOE-DAC 的 Target、Observe、Estimate、Decide、Act、Check 每个阶段都包含不可省略的
模型判断。确定性控制层不是阶段替代器，而是为模型阶段提供可验证事实、机械执行能力和硬约束。

基本不变量：

> 模型决定“做什么、为什么、是否足够”；控制层负责“按规范执行、保存、登记和校验”。

任何阶段都不得因为存在确定性规则而绕过模型；任何纯机械操作也不得被包装成一个需要模型反复
规划、确认和验收的 Action。

## 六阶段职责矩阵

| 阶段 | 模型的关键判断 | 确定性控制层职责 |
| --- | --- | --- |
| Target | 理解用户意图，定义正向/负向目标和验收语义，识别实质歧义 | 分配 ID、补齐协议默认值、校验 Schema、移除用户未提出的路径和数值硬约束 |
| Observe | 决定需要观察什么、选择来源和技能、区分事实/推断、判断事实是否充分 | 执行已选工具，创建 Session 证据目录，保存截图，计算哈希，登记工具原始元数据 |
| Estimate | 判断可行性、风险、成本、信息缺口以及是否需要重新观察 | 补齐纯记账字段、校验枚举和字段结构、记录阶段耗时与用量 |
| Decide | 选择解决路径，生成有依赖关系的 Action 图，确定预算和升级条件 | 分配 Action/断言 ID，校验 DAG，删除“复制证据”“再次验收”等机械或重复 Action |
| Act | 执行 Action 的语义工作，生成报告、代码或决策结果，并根据失败反馈调整 | 调用受限 Executor，原子写入 Artifact，关联证据，记录尝试与预算 |
| Action Check | 判断 Action 结果在语义上是否正确、完整并实现 Action 目标 | 计算文件存在、哈希、包含、长度、证据引用等硬事实；硬事实交给模型审查但不可被改写 |
| Target Check | 判断整体结果是否真正实现 Target，并检查负向约束 | 汇总验收硬事实、持久化结果和完成 Artifact；失败后按预算触发恢复 |

Check 在工程上分为 Action Check 与 Target Check，因此模型判断与确定性预检查也分别执行。

## Observe 的正确流程

```text
模型读取 Target 和技能索引
→ 模型判断需要访问哪个来源并选择工具
→ 运行时执行工具
→ 控制层把截图保存到 trace/sessions/<session>/screenshots/
→ 控制层登记 path、sha256、size、URL、page_title、body_text 等原始元数据
→ 模型依据工具结果提交 Observation，判断 facts 与 unknowns
```

控制层不能仅因用户输入里包含 URL 就直接构造 Observation。相反，模型也不能决定截图应该复制到
哪个内部目录、如何计算哈希或是否需要再做一次“归档 Action”。

## Check 的正确流程

```text
控制层计算硬事实
→ 模型审查硬事实，并判断语义正确性与整体覆盖度
→ 合并结果（硬事实优先，模型补充语义判断）
→ 状态机决定通过、预算内自动恢复或请求人类
```

预算内的重试、内部 Plan/断言冲突、字段形状不一致都不是新的用户授权，不应打断人类。只有缺少
用户才能提供的信息、凭证或新增高影响授权时，才进入 `waiting_human`。

## 当前控制层结构化范围

- canonical Session 目录和 Artifact 目录分配；
- 截图等文件的保存、路径约束、哈希和证据注册；
- event/operation/messages/evidence 的追加式落盘；
- Schema、枚举、DAG、预算和状态转换验证；
- 用户未提出的 `./evidence/`、复制/归档 Action 和重复验收 Action 清理；
- 用户未明确给出的数值限制不提升为硬验收标准；
- 网络/模型运行错误归一化后进入有预算的自动恢复；
- 确定性断言计算，以及与模型语义审查结果合并。
